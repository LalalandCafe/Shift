# SHIFT Security & Quality Audit — 2026-09-04

Scope: full repo at `/workspaces/Shift`. Read-only. All findings verified against
current source, not inferred from file names or prior notes. No prior audit
report exists inside this repo — `BRIEF.md` references a `SHIFT-database-audit.md`
that was never committed here. This report therefore uses the "known issues"
list supplied for this audit (which lines up with `BRIEF.md`'s package
descriptions and git history) as the prior baseline, and calls each one
FIXED / PARTIALLY FIXED / STILL OPEN with file:line evidence.

---

## Executive summary

- **Most of the dangerous data bugs from the last audit are genuinely fixed.** The Toast sync no longer deletes-before-inserts, timezones are now resolved per store instead of a single hardcoded offset, and the California midnight bug is closed on both the write and read side. This was real, careful remediation work — it shows in the code's own comments.
- **The one unresolved architectural gap is authorization, and it's a ticking clock, not a today problem.** Right now the app only lets Admins in at all, so nothing leaks. But almost none of the 30 API routes have their own access check — they rely entirely on that one blanket rule. The region/store-level scoping code was built but never connected to anything. The day Entra turns on regional groups, a Texas manager can pull California labor numbers just by changing a URL parameter, with no code change needed to make that possible — it's already possible today in every route except three.
- **The dashboard can quietly disagree with itself.** Three different files each maintain their own copy of "which hours count as billable," and they've already drifted apart in a demo endpoint ($19 vs $15 SPLH for the same shift data). It hasn't reached the live dashboard yet, but the pattern that caused it is still there in production code.
- **A well-intentioned fix created a new failure mode.** The fiscal calendar used to fail silently (blank numbers, no error). It now fails loudly — by crashing the entire app at startup the moment the calendar table runs out, currently scheduled for December 27, 2027. Loud is better than silent, but with no staging environment, a hard crash on a specific future date deserves a safety net, not just a comment.
- **Overall this is a well-run, actively-maintained codebase.** The findings below are concrete and fixable, most of them cheaply, and none of them are "rewrite it" problems.

## Findings detail

### AUTH-1 — Critical — Route-level authorization is unwired

**What.** `middleware.js:90-95` is the only access-control check that runs for
almost every route in the app:

```js
if (user.role !== "admin") {
  if (pathname.startsWith("/api/")) {
    return NextResponse.json({ ok: false, error: "Not allowed" }, { status: 403 });
  }
  return NextResponse.redirect(new URL("/login?error=scope", request.nextUrl));
}
```

This is binary: admin or nothing. Below it, `lib/require-session.js` defines
exactly the machinery a regional/store rollout would need —
`requireSession()`, `requireGrp(session, grp)`, `accessFromSession()` — with a
docstring explaining the intended pattern ("Every handler that touches store
data calls this first"). A repo-wide search confirms **zero call sites**:

```
grep -rn "requireSession\|requireGrp\b" --include="*.js" . | grep -v lib/require-session.js
→ (no results)
```

`lib/permissions.js`'s `filterStores`/`canSeeGrp` — the functions that would
actually filter a store list down to what a regional user may see — are
likewise imported nowhere except by the unused `require-session.js`. Of the
~30 route handlers under `app/api/`, only three do any route-local check at
all: `app/api/stores/route.js` (`requireAdmin` on `PATCH`), `app/api/report/route.js`
(strips two fields for non-admins, but does not filter stores), and
`app/api/sssg/route.js` (`requireAdmin`, with a comment explicitly
acknowledging this is redundant defense-in-depth on top of middleware). Every
other data route — `dashboard`, `drive-thru`, `kitchen-day`, `kitchen-trend`,
`kitchen-week`, `throughput`, `store-trend`, `export`, `forecast`,
`forecast/hourly` — has no `sessionFrom`/`requireGrp` call whatsoever, and all
accept a `storeCode`/`store` query parameter with no ownership check against
the caller's session.

**Why it matters.** `resolveAccess()` in `lib/permissions.js` and the
middleware's own comments (`middleware.js:86-89`) already describe the
intended next state: `TX-TN` and `CA-AZ` Entra groups resolve to a `regional`
role with a `grps` array, and `middleware.js` line 90 is exactly the line that
will need to change to let that role past the gate. When that happens, unless
this finding is fixed first, a signed-in regional user hits `/api/store-trend?storeCode=<any code>`
or `/api/drive-thru?storeCode=<any code>` and gets full data for a store
outside their region — a Texas GM reading California labor and sales numbers
— with **no code change required to make that possible**. The scoping code to
prevent it already exists in the repo; it's just never called. This is worse
than a typical "add auth" finding because the fix is not new plumbing, it's
wiring up plumbing that was already built and then abandoned mid-rollout —
meaning the gap is easy to miss precisely because it looks like the problem
was already solved.

**Fix.** Wrap `lib/require-session.js`'s `requireSession()` +
`requireGrp(session, grp)` (or a single combined helper) into every data
route that accepts a `storeCode`/`store` parameter, resolving the store's
`grp` first (one `stores` lookup, already cached-list-shaped) and checking it
against the caller's session before running the query. Do this as one PR
that touches every route the same way, not a per-route patch — the same
lesson `BRIEF.md` Package 4 already drew and then didn't fully execute.

**Effort:** M (the helper exists; this is retrofitting ~12 routes with the
same three-line call plus a grp lookup).
**Risk of fixing:** Low technically (additive checks, admin behavior
unchanged since `allStores === true` short-circuits everything), but touches
every route in one PR with no staging — test each route manually as an admin
after the change, since a wiring mistake here fails closed (403) rather than
open, which is the safe direction to err but still needs a full manual pass
given the audience is a live production dashboard 60 managers use daily.

### AUTH-2 — High — `planned_hours` writes/deletes have no route-level auth

**What.** `app/api/forecast/route.js` `POST` (lines 30-65) and `DELETE`
(69-105) write and delete rows in `planned_hours` with no `requireAdmin`,
`sessionFrom`, or any auth call at all — contrast with `app/api/stores/route.js`'s
`PATCH`, which explicitly gates writes:

```js
// app/api/forecast/route.js:30-37
export async function POST(request) {
  try {
    const body = await request.json();
    const { storeCode, days } = body;
    if (!storeCode || !Array.isArray(days)) { ... }
```

No auth check anywhere in the file.

**Why it matters.** Today this is only reachable by an admin, same as
everything else, because of the blanket middleware gate. But this is a
*write* path, not a read — once AUTH-1 is fixed and regional/store roles are
let through middleware, a regional user could overwrite or delete another
region's planned labor hours (`DELETE /api/forecast?store=<any code>&weekStart=...`
clears an entire week) with zero server-side check that the store belongs to
them. This is a strictly worse failure mode than a read-only leak.

**Fix.** Same shared guard as AUTH-1, applied here with a `requireGrp` check
before the `upsert`/`delete` — this route should be first in line when
AUTH-1 is retrofitted, since it's the only unauthenticated write/delete
endpoint in the app that touches store-attributed data.

**Effort:** S. **Risk of fixing:** Low — purely additive.

### DATA-1 — High — Fiscal calendar hard-crashes the app on expiry

**What.** `lib/fiscal.js:97-110`:

```js
// Fails loudly, at import time, the moment today falls in a gap FISCAL_PERIODS
// doesn't cover ...
if (!getPeriodForDate()) {
  throw new Error(
    "FISCAL_PERIODS has no period covering today (" + ... + "). Every PTD figure " +
    "on the dashboard and in the daily email will read empty until FISCAL_PERIODS " +
    "is extended - add the missing period(s) in lib/fiscal.js."
  );
}
```

This is a real, deliberate fix for a real prior bug (a May 2026 gap silently
blanked PTD figures — documented at `lib/fiscal.js:3-8`). The calendar now
runs through `2027-12-26` (`lib/fiscal.js:45`). But the file's own comment
(lines 10-20) is explicit that the 2027 dates are a mechanical extrapolation,
**"THIS HAS NOT BEEN VERIFIED against whatever calendar Finance/Ops actually
publishes for 2027"**, and does not check for a 53-week year.

**Why it matters.** The throw is at *module import time* — this is not a
per-request error handled by a route's try/catch, it fires the instant
anything imports `lib/fiscal.js`, which is nearly every report-building path
(`lib/report.js`, `lib/throughput.js`, and transitively the dashboard, the
export route, and the daily email). If nobody has extended `FISCAL_PERIODS`
past `2027-12-26` by the time that date arrives, every one of those routes
goes down hard, simultaneously, in production, with no staging environment
to have caught it beforehand and (per OBS-1) no active alert to flag it
before managers notice the whole app is broken. Silent-blank-PTD was a bad
failure mode; total-app-outage-with-no-warning is a different bad failure
mode, not obviously an improvement at this blast radius.

**Fix.** Keep the fail-loud principle, but change *where* it fires: move the
check out of synchronous module-load and into a scheduled check (a small
addition to an existing daily/weekly GitHub Action, or a lightweight
`/api/health` route) that alerts with real lead time — e.g. "fewer than 60
days of `FISCAL_PERIODS` coverage remain" — rather than a hard crash the
moment coverage actually runs out. Also independently confirm the 2027 dates
against Finance's real published calendar per the file's own outstanding
comment.

**Effort:** S–M. **Risk of fixing:** Low — this is strictly reducing blast
radius versus the current behavior.

### BIZ-1 — Medium — Three independent billable-hours exclusion lists

**What.** `lib/calc.js:20-26` (`exclReason`), `lib/report.js:84-90`
(`exclusionReason`), and `lib/throughput.js:97-103` each hardcode their own
list of job titles excluded from labor-hour totals. `report.js` and
`throughput.js` match each other; `calc.js` additionally excludes
`"event support - la"`, which the other two do not.

**Why it matters.** `calc.js`'s exclusion logic is wired only into the demo
endpoints (`app/api/demo/day/route.js`, `app/api/demo/email/route.js`); the
live dashboard, Week View, and daily email all run on `report.js`/`throughput.js`'s
narrower list. Concrete example: an employee titled "Event Support - LA"
works 8 hours at a store where everyone else logged 32 hours against $600 in
sales.

- Live report/email path: hours = 32 + 8 = 40 → SPLH = 600/40 = **$15**.
- Demo path: that employee is excluded → hours = 32 → SPLH = 600/32 = **$19**.

Nothing user-facing is wrong today — the demo is clearly labeled as a demo.
The risk is that this is a landmine: if `calc.js`'s `aggregatePayroll` is ever
reconnected to a real ingestion path (a natural-looking refactor, since it's
the "cleaner" of the three implementations), it will silently start excluding
hours the live report currently counts, changing real SPLH numbers with no
warning.

**Fix.** Extract one shared `isExcludedFromLabor(jobTitle)` function, decide
once whether "Event Support - LA" should be excluded (this is a business
decision, not a coding one — flag it explicitly), and have all three files
import it.

**Effort:** S. **Risk of fixing:** Medium *if* the "Event Support - LA"
question is resolved by including it — that would move a real number on the
live dashboard/email for any store using that job title. Verify with a
side-by-side report run before and after, not a same-day ship.

### DATA-2 — Medium — Dead-but-deployed legacy Toast routes still carry the timezone bug

**What.** `app/api/toast/cron/route.js:48-49` and
`app/api/toast/sales-compare/route.js:60-61` still hardcode:

```js
const startDate = isoDate + "T00:00:00.000-0500";
const endDate = isoDate + "T23:59:59.000-0500";
```

— the exact bug already fixed in the live path
(`app/api/toast/sync-store/route.js`'s `localDayWindowForToast`, which
resolves each store's real IANA timezone). Neither route is called by any
scheduled workflow — `.github/workflows/*.yml` only ever calls
`/api/toast/sync-store` — but both remain deployed and reachable (gated by
`x-sync-secret` + the middleware machine allowlist). `sales-compare/route.js`
additionally fetches orders one-by-one and silently discards failures
(`catch(e) { return null }`), which `sync-store`'s single paginated call does
not do.

**Why it matters.** If either route is ever triggered manually (a developer
debugging, a bad copy-paste of a curl command, a future automation that
targets the wrong endpoint), a California or Arizona store's labor window
would be requested 2–3 hours off from local midnight-to-midnight, silently
producing wrong hours for that store/day with no error — the exact bug class
the rest of the sync pipeline was carefully fixed against.

**Fix.** Confirm with the team whether these routes are intentionally kept as
manual fallback tools; if not, delete them (per MAINT-2, same reasoning). If
they must stay, apply the same `localDayWindowForToast` fix as `sync-store`.

**Effort:** S (delete) or S–M (fix in place). **Risk:** None if deleting —
nothing calls them.

### BIZ-2 — Medium — Inverted over/under-budget sign convention

**What.** `lib/calc.js`/`lib/report.js` compute `overUnder = allowed - actual`
(positive = under budget); `components/Forecast.js:537` computes
`diff = actual - allowed` (positive = over budget) — the opposite raw sign
for the same real-world situation. Each file's own display logic is
internally consistent with its own sign (colors and labels match), so
nothing renders wrong today.

**Why it matters.** This is a landmine, not a live bug: the moment someone
passes an `overUnder` value from `report.js` into `Forecast.js`'s
`diff > 0 → red / diff < 0 → green` logic (or builds a shared component that
consumes both), a store 2 hours over budget would render green.

**Fix.** Pick one sign convention, document it with a one-line comment at
each site, and consider a shared `formatVariance(allowed, actual)` helper
before any future work merges these views.

**Effort:** S. **Risk:** Low, but touches display logic in two places —
verify visually, don't ship blind.

### PERF-1 — Medium — The caching layer is dead code

**What.** `lib/cache.js` defines `memo(key, ttlMs, fn)`, with comments
describing exactly the problem it was built to solve (many managers loading
the dashboard for the same date at once; 10-minute TTL for closed days,
30-second TTL for the live day). A repo-wide search:

```
grep -rn "memo(" app lib   →  only the definition in lib/cache.js itself
```

`memo` is never called. `buildDailyReport`, the dashboard route, and the
export route all run a full, uncached round of Supabase reads on every
request.

**Why it matters.** With ~60 managers potentially loading the same dashboard
date within the same minute, every one of those page loads independently
re-runs the same paginated `toast_labor_shifts`/`daily_sales` scans and
review rollups that `lib/cache.js` was explicitly written to avoid.

**Fix.** Wire `memo()` around `buildDailyReport` (or its Supabase-facing
sub-calls) in `lib/report.js`, using the TTLs already designed for it.

**Effort:** S–M. **Risk of fixing:** Medium — changes response staleness
semantics on the most-viewed page in the app. Don't ship same-day; verify the
TTL choice against how quickly a mid-shift number needs to update.

### PERF-2 — Medium — `/api/export` re-reads overlapping labor windows

**What.** `app/api/export/route.js:30-36` runs 7 `buildDailyReport` calls in
parallel, one per weekday. Because each day's WTD window reads from the
week's Monday through that day, Sunday's call re-reads the entire week that
Monday's call, Tuesday's call, etc. already read — roughly 28 day-equivalents
of labor data fetched to produce 7 real days, on a route with
`maxDuration = 60`.

**Why it matters.** This is the export route most exposed to Vercel's
function timeout and to PostgREST load, and it scales with 35 stores × a
full week's shift history on every export click.

**Fix.** Build the week's data once (a single WTD-window fetch per store)
and derive each day's slice from it, rather than calling `buildDailyReport`
per day.

**Effort:** M. **Risk:** Low-Medium — this changes the internals of a
report builder used by other callers; verify export output is byte-for-byte
equivalent before shipping.

### SEC-1 — Medium — Orphaned Toast debug routes have no route-level auth

**What.** `app/api/toast/{orders-debug,sales-debug,token,jobs,labor,labor-readable}/route.js`
have zero `sessionFrom`/`requireAdmin`/`x-sync-secret` checks in the handler
itself. They are not in `middleware.js`'s `MACHINE` allowlist, so today they
require a signed-in admin session (same blanket gate as everything else) —
not open to the internet. `sales-debug` fires bursts of Toast API calls (3 at
a time) with no rate limiting beyond Toast's own; `labor`/`labor-readable`
return raw employee time-entry data (names, job titles) for any date range
with no pagination guard.

**Why it matters.** These read as leftover integration-debugging endpoints
from the original Toast build-out. They carry no unique protection of their
own — any admin session, or a future regional/store session if AUTH-1 isn't
fixed first, can reach them.

**Fix.** Delete the ones no longer used for active debugging; for any kept,
require `x-sync-secret` or `requireAdmin` explicitly rather than relying
solely on the blanket gate.

**Effort:** S. **Risk:** Low — verify nothing internal still depends on them
before deleting.

### MAINT-1 — Medium — Week View's table layout has no single source of truth

**What.** `app/globals.css:3420-3474` hand-maps 18 table columns to widths via
positional CSS selectors:

```css
.wk-legacy table.grid th:nth-child(1),
.wk-legacy table.grid td:nth-child(1) { width: 184px; ... }
```

with a comment block just above (lines 3420-3425) manually documenting what
each column index means ("10 wtd (o)/u, 11 training, 12 trainee..."). Fully
independently, `lib/email-generator.js:40-79` builds the *same* 18-column
table as a raw HTML string, with its own hand-written column order — no
shared constant, no shared component, no test comparing the two.

**Why it matters.** This is precisely why `BRIEF.md` freezes
`components/WeekView.js` and the `.wk-legacy` CSS scope ("It is frozen
deliberately because `/api/email` mirrors its markup. Changing it breaks the
daily email.") — the fragility is real and already recognized, which is why
it was frozen rather than fixed. Any future column add/remove/reorder in one
place and not the other silently breaks either the live table's styling
(wrong column gets wrong width/color via `nth-child`) or the daily email's
layout, with nothing to catch the mismatch except a human noticing.

**Fix.** Not a same-day fix given the freeze. When this is next touched,
extract the column list (index → label → width) into one shared array both
`WeekView.js`'s CSS-generation (or a CSS-in-JS approach that doesn't need
`nth-child`) and `email-generator.js` can read from.

**Effort:** L (touches the frozen file and the email it mirrors).
**Risk:** High if rushed — this is exactly the file the team already
identified as too fragile to touch casually. Do not attempt without a full
manual comparison of the live table and a real sent test email afterward.

### MAINT-2 — Low — Dead code with live landmines

**What.** `lib/aggregate.js`'s `aggregateWTD`/`ptdMetrics` are unused
anywhere in the codebase (confirmed by repo-wide search) and unguarded
against `target <= 0` — unlike `report.js:399`'s explicit `if (t > 0)` guard,
a zero/null target here produces `Infinity`/`NaN`. `lib/require-session.js`
is unused (see AUTH-1) but should be *reused*, not deleted, since it's the
right building block for that fix.

**Why it matters.** Unused code with a real bug in it is an attractive
nuisance — the moment someone reaches for "a WTD aggregator" and finds
`lib/aggregate.js` already exists, they'll wire in the buggy one instead of
`report.js`'s already-correct, already-live version.

**Fix.** Delete `lib/aggregate.js` if truly unused; keep and complete
`lib/require-session.js` as part of the AUTH-1 fix rather than leaving it as
an implemented-but-abandoned dead end.

**Effort:** S. **Risk:** None — deleting unreferenced code.

### OBS-1 — Low — No active failure-alerting channel

**What.** All six GitHub Actions workflows correctly check the response
body's `ok` field (not just HTTP 200), retry, verify full store coverage
against the unfiltered `stores` table, and `exit 1` on any failure — this is
genuinely well-built. But none of them post to Slack, email, or any other
active channel; failure is visible only via GitHub's own job-failure UI and
default email-to-watchers. Separately, `app/api/toast/cron-trigger/route.js:31-46`
dispatches each store's sync with `fetch(...).catch(() => {})` and does not
await completion before returning.

**Why it matters.** A failed hourly sync at 2am is currently detected — the
job goes red — but nobody is actively notified unless someone is watching
the Actions tab. In a "no staging, ships straight to prod" environment, silent
failure detection is a soft version of the same problem the rest of this
audit spent most of its effort eliminating elsewhere.

**Fix.** Add a Slack (or equivalent) webhook step on failure to each
workflow — cheap, additive, no behavior change to the sync logic itself.

**Effort:** S. **Risk:** None — purely additive, safe to ship any day
including a Friday.

### PERF-3 — Low — No committed schema, migrations, or indexes

**What.** `supabase/schema.sql` is 16 lines and defines exactly one table
(`toast_labor_shifts`) with two indexes. `daily_sales`, `hourly_sales`,
`daily_transactions`, `kitchen_metrics`, `manual_adjustments`,
`planned_hours`, `metric_targets`, `tattle_reviews`, `stores`, and every
other table this codebase reads and writes have zero committed
definitions. There is no `supabase/migrations` directory at all — this
matches `BRIEF.md`'s own section 11.1 note that establishing a migration
baseline is known-missing, deliberately deferred, separate work.

**Why it matters.** Every query in `lib/report.js` and
`app/api/drive-thru/route.js` filters/orders by `store_code`/`business_date`
or `store_id`/`clock_in` pairs; whether a composite index backs those
filters cannot be verified from this repo — it may or may not exist live in
Supabase, and nobody reviewing this code can tell. This is a finding
independent of whether performance is currently fine.

**Fix.** Not new work to prescribe here — `BRIEF.md` already flagged this as
its own project. Reiterating it here because it also blocks verifying
several other findings (see Needs Manual Verification).

**Effort:** L (establishing a migration baseline, out of scope for a quick

### DATA-3 — Low — Supabase admin client instantiated at import time

**What.** `lib/supabase.js:3-9`:

```js
export const supabaseAdmin = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL,
  process.env.SUPABASE_SERVICE_ROLE_KEY,
  { auth: { persistSession: false, autoRefreshToken: false } }
);
```

Module-level, not inside a function. This is a common and generally
reasonable pattern for serverless connection reuse, but it means a missing
or invalid `SUPABASE_SERVICE_ROLE_KEY` breaks every route that imports this
file at cold start, rather than failing only the route that actually needed
it — and nearly every route imports it.

**Why it matters.** Low likelihood, high blast radius: one bad env var
change in Vercel could take the entire API surface down simultaneously, with
no staging to catch the misconfiguration first.

**Fix.** Not urgent — flagging as a known trade-off rather than a bug. If
ever revisited, a lazy-init factory would contain the blast radius to
whichever route first needs it.

**Effort:** N/A (accepted trade-off). **Risk:** N/A.
